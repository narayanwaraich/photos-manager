# TASK-0B: EmbeddingGemma 2 runtime spike

**Phase:** 0 · **Branch:** `task/0B` · **Depends on:** nothing (run in a separate conversation from 0A; may run in parallel)
**Orchestrator note:** A measurement task, not product code. It decides how the app runs EmbeddingGemma 2 locally (ONNX Runtime, llama.cpp, or a user-supplied endpoint), which artifact and quantization to use, which stored dimension to default to, and whether the vision encoder can be loaded on demand. Nothing here is wired into the Tauri app. If no runtime passes, the product ships without semantic search (spec §9.1) and this task has still succeeded.

- `AGENTS.md`
- `IMPLEMENTATION_SPEC.md` §9.1 (all), §5.2 (`asset_embeddings`), §7.1 (preview derivative), §15 (vector search target)

## Facts to verify, not assume (from Google's model card, developer guide and tech report as read by the orchestrator)
- EmbeddingGemma 2 is Apache 2.0, multimodal (text, image, video, audio), and embeds into **one shared 768-d space**; Matryoshka dims 768/512/256/128; 8,192-token shared context; modular loading (text ≈ 270M params, text+image ≈ 440M, full ≈ 740M); text-only queries match full-model document vectors and adding an encoder needs no re-embedding.
- Text uses task prefixes (`task: search result | query: …`; documents `title: … | text: …`, `title: none | text: …`). **Images get no prefix.** Image default is 280 tokens; the budgets reported are 70/140/280/560/1120.
- The model card warns against fp16 activations; bf16/fp32 recommended. QAT int4 checkpoints exist.
- Reported (not yet verified by us): ONNX exports from `onnx-community` with total sizes ≈ fp32 2.9 GB, fp16 1.5 GB, q8 0.85 GB, q4 0.47 GB, q4f16 0.43 GB, documented for Transformers.js; output named `sentence_embedding`; GGUF conversions exist (ggml-org and community, with an mmproj for multimodal); MLX/CoreML conversions exist.
Treat all of the above as hypotheses. Where the spike contradicts them, report the contradiction.

## Goal
Using a Python reference implementation as ground truth, determine for each candidate runtime whether it reproduces the reference vectors for text **and** images, at what speed and memory, and recommend one runtime, one artifact (with checksum), one default stored dimension, and one vision token budget.

## Extra network permission
In addition to the AGENTS.md list: `huggingface.co` (model files), `github.com/ggml-org/llama.cpp` and `github.com/pykeio/ort` (source or release binaries), `pypi.org` for the reference environment. Nothing else.

## In scope
1. **Provenance.** Find the official model page and its license text. List every candidate artifact repo (official, `ggml-org`, `onnx-community`, `unsloth`/community GGUFs, MLX): owner, commit hash, files, sizes, SHA-256, stated license, and whether *official* or *community*. List before downloading. Recommend one; the owner approves it in the review before any later task uses it.
2. **Reference harness (R4).** `spikes/embeddings/` with a git-ignored `.venv`. Install `sentence-transformers` (or the officially documented loader) and the official weights. fp32 on CPU (bf16 only if verified safe on this hardware). **Never float16 for reference vectors.** One documented command regenerates reference vectors at 768 d for the fixture set (text with the documented prefixes, images without).
3. **Fixtures** (generated by script; no real photos): ~20 base images with distinct, describable content (shapes, colours, rendered text, gradients, patterns) and ~10 text queries that should retrieve specific ones; near-duplicate variants of each base (resized, JPEG q90/q60, crop 10%/25%, rotate 90°, brightness/contrast, light blur); distractor pairs that look alike but differ. If the owner placed images in `spikes/embeddings/local-fixtures/` (git-ignored) you may read them read-only locally; never upload or commit anything derived from them. If absent, say so.
4. **ONNX path (R2).** Download the candidate ONNX variants you listed (at least q8 and q4; fp32 as the baseline if memory allows). Determine the actual input names/shapes and the exact image preprocessing (resize/crop policy, normalisation, patching, token budget) by inspecting the model files and the reference implementation, not by guessing. Run via the Python `onnxruntime` first, then confirm the same files load in Rust through `ort` in a standalone spike crate under `spikes/embeddings/ort-probe/` (not in `src-tauri/`). Test fp16 ONNX only to measure its cosine to the fp32 reference; do not recommend it unless it passes.
5. **llama.cpp path (R1).** Identify which llama.cpp release/commit supports EmbeddingGemma 2 (verify; do not assume). Run the embedding server with the candidate GGUFs (Q8_0, a 4-bit variant, bf16 reference if available). Test **text** first, then **image** through whatever the build supports (mmproj). If mainline cannot produce image embeddings, document exactly what is missing and whether a fork/patch exists. Do not adopt an unreviewed fork; report it.
6. **Endpoint path (R3).** Briefly check whether Ollama or LM Studio expose this model through an OpenAI-compatible `/v1/embeddings` endpoint with image input. Timebox to a short note; do not build anything.
7. **Measurements** on this machine (record CPU/GPU, RAM, OS, build flags, thread counts):
   - cosine vs reference for identical inputs, text and image, per runtime/quantization (report min/mean);
   - per-text and per-image latency, throughput on 512 px previews, peak RSS, model load time, whether the vision encoder loads on demand and what memory it adds;
   - at 768/512/256/128 d (truncate then L2-normalise): text→image top-1/top-5 on the fixture queries, near-duplicate recall/precision at several cosine thresholds, and how the distractor pairs score;
   - vision token budget 140 vs 280 (and one higher value if exposed): quality and latency;
   - preprocessing parity: a deliberate wrong preprocessing (for example wrong normalisation) to show how much quality it destroys, so that parity tests in Phase 4B are meaningful.
8. **Recommendation** in `docs/embedding-spike.md`: runtime, exact artifact + quantization + checksum, default dimension, token budget, memory and disk footprint, download-on-consent and packaging plan (what ONNX Runtime or llama.cpp binaries must be bundled per OS), licence checklist for the owner (link the licence pages; do not paste licence text), a proposed `ModelInfo`/`model_revision` string format, and what stays unknown (video/audio untested).

## Out of scope (do not do)

## Acceptance criteria
- [ ] Provenance table complete; every downloaded file has SHA-256 and source URL.
- [ ] Reference vectors reproducible by one documented command.
- [ ] Cosine-vs-reference for text and image for each runtime/quantization tested, or a clear statement that image embedding could not be run and why.
- [ ] Real ONNX input names and image preprocessing documented, with the Rust `ort` probe result.
- [ ] Latency, throughput, peak memory and on-demand vision-encoder loading numbers, with hardware stated.
- [ ] Retrieval and near-duplicate numbers at 768/512/256/128 d, and 140 vs 280 token budget.
- [ ] A recommendation, or an explicit "no viable self-contained runtime found" with the evidence.
