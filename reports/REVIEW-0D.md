## Decisions (orchestrator; recorded in STATUS as D10 and D11)
- **D10: libvips stays the only image engine on both OSes. No macOS ImageIO seam in v1.** The agent's report recommends ImageIO for macOS. I do not take that route: it adds a second decode path whose colour, orientation and HDR handling would differ from libvips on one OS only, it needs new unsafe FFI code and a spec change, and it does not help Windows at all (which still needs libde265). It stays a documented fallback, to be used only if an own libvips build on macOS fails and you agree.
- **D11: HEIC-capable libvips comes from our own pinned build recipe, Windows first.** Windows is first because the laptop cannot decode HEIC even in `pnpm tauri dev` (your Mac can, through Homebrew), and because it is the harder half. TASK-0E uses the same upstream builder that produces the zip we already use (MXE), with libde265 on and x265 off, built by a manually started workflow and stored as a checksum-pinned release asset in your repo, so the long build runs once, not on every push. macOS is TASK-0F, written after 0E teaches us how the recipe behaves; the two candidates are rebuilding only `libheif` without x265 (stopgap, small) or a full own build (cleaner, removes the GPL harvest).
- **Rejected: replacing `libheif.dll` with an MSVC/clang-built one inside the MXE zip.** It mixes toolchains and C++ runtimes, reintroduces the Visual C++ runtime question that 0C closed with a static CRT, and has no packaging story.
