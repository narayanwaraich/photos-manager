## Findings

### Must fix: code and tests (the agent does these)

1. **Four production `unwrap`/`expect` calls, one of them on the start-up path.** `init()` (called from `startup_with_path`) takes `INIT_MUTEX.lock().unwrap()`; `generate_thumbnail` takes `VIPS_OP_MUTEX.lock().unwrap()`; `get_vips_app()` and `impl Default for VipsImageProcessor` use `.expect("BUG ...")`. The task allows only the two spike-handler calls in `lib.rs`. The report's "zero `unwrap`/`expect` on the start-up path" is false, and its own Concept 2 cites `vips.rs:77`, which is one of them.
   Fix: (a) both mutexes guard `()`, so a poisoned lock holds no broken data; use `lock().unwrap_or_else(std::sync::PoisonError::into_inner)` through one small helper, with a one-line comment saying why that is safe. (b) Make the proof of initialisation part of the type: `pub struct VipsImageProcessor { _app: &'static VipsApp }`, built in `new()` after `init()?` by `VIPS_APP.get().ok_or(ImageProcessorError::Processing(...))`. Then `get_vips_app()` and the `Default` impl (nothing calls it) are deleted and no `expect` is left. `smoke.rs` and the spike handler already handle the `Result`.

2. **`test_vips_error_buffer_no_stale_text` cannot fail.** It asserts only that both messages are non-empty; the closing comment says the real check is "best-effort". Add the assertions the task asked for: each message names its own file and the second does not carry the first (libvips normally puts the file name in the message; if the pinned build does not, use two failures whose texts differ and compare each with what the same failure reports on its own). Then show it failing once: temporarily replace `read_vips_error` by a read that does not clear the buffer, paste the failing run, revert (lesson 9: a test you have never seen fail may not test anything).

3. **The `IpcError` leak test skips a variant and checks secrets that are never in the samples.** (a) `CatalogueError::Migration` has no sample, so `database_migration` is never exercised (`sqlx::migrate::MigrateError::VersionMissing(7)` builds one). (b) `secret_path` is not inside any sample, so its assertion cannot fail; the data of `PlatformMismatch`, `InvalidEnum("bogus_enum_value")`, `SizeOutOfRange` and `Database(..)` is never asserted either. Make the table `(variant, [strings that must not appear])`, one row per variant, and put the sensitive strings into the variant's data. (c) Make "every variant" a compile-time fact: a test-local function with an exhaustive `match` over `CatalogueError` (no `_` arm) that returns the sample, so a new variant stops the build. (d) Add the missing error-path test: a pool that has been closed (`pool.close().await`) makes `app_info(&pool)` return an `IpcError` with code `database` and the fixed message.

4. **The drift guard compares TypeScript with a list typed by hand.** `rust_codes` in `test_error_codes_sync_with_typescript` is a second copy of the codes, so a new `CatalogueError`, `PathError` or `StartupError` variant with a new code passes the test unchanged. Also, `assert!(!msg.is_empty())` cannot fail because `fixed_message_for_code` has a `_` arm that returns a non-empty text. Fix: put the list where the codes live (one `pub const ALL_CODES: &[&str]` per error type, or one in `commands/error.rs` next to the match), build the test from it plus finding 3(c), and assert that every code except `internal` has a message different from the `internal` one. Keep the TS side as it is.

5. **`read_vips_error`: wrong SAFETY text, a comment that contradicts the code, and a possibly redundant call.** The SAFETY comment says `g_strdup` "returns empty string for NULL input"; `g_strdup(NULL)` returns NULL (the code handles null, so only the comment is wrong). The doc comment says the mutex around every libvips call is "impractical" and the race "accepted", while `generate_thumbnail` holds `VIPS_OP_MUTEX` from the thumbnail call to the end of the function (decode, WebP save and `create_dir_all`). It also says the pointer is freed with "`libc::free` / `g_free`"; only `g_free` is right (two allocators on Windows). Finally, libvips documents `vips_error_buffer_copy` as copy-and-clear; if that holds for the pinned fork, the extra `vips_error_clear()` is redundant and, outside the lock, could throw away another thread's text. Check the fork's source (the task said to), then: rewrite the comments so they describe what the code does, drop the second call if it is redundant, and state in the report the exact race window that remains (the task's Part E2 asked for it; any libvips call outside `generate_thumbnail` that can set the buffer is outside the lock) and the cost: one thumbnail at a time for the whole process (see risk 52).

6. **Start-up failures lose their detail, and the runtime-error dialog shows raw text.** `show_startup_error_dialog` shows the fixed message plus the code, which is right, but nothing writes the `StartupError` itself anywhere, so `catalogue_open_failed` can never be diagnosed. Add `eprintln!("startup failed [{}]: {}", err.code(), err)` before the dialog (stderr is visible under `pnpm tauri dev`; nothing crosses the IPC boundary). The second dialog, after `builder.run(...)` fails, prints `format!("Application runtime error: {err}")`: raw error text and no code, against the policy "short plain-language message and the stable code". Use a fixed sentence, print the detail with `eprintln!`, and say in the report which code the dialog carries (a new code means the TS list and finding 4 change with it).

7. **ExifTool: the version test is too weak and the Windows commands are incomplete.**
   - `test-exiftool-version.mjs` only checks that `ci.yml` and the docs *contain* the pinned version (the second branch of its `||` makes the first one pointless). A half bump passes: `ci.yml` names the version twice (`exiftool-13.61_64.zip` for Windows, `Image-ExifTool-13.61.tar.gz` for macOS); change only the macOS one to 13.62 and the test still finds `exiftool-13.61` and stays green. Extract every `ExifTool` version from both files with a regular expression and assert each equals `PINNED_EXIFTOOL_VERSION`; do the same for the two SHA-256 values the module holds (nothing compares them with `ci.yml` today). Show it failing against a half bump, paste, revert.
   - The Windows lines in `docs/native-dependencies.md` §5.3 and in the `fixInstructions` text of `exiftool-version.mjs` omit two steps that `ci.yml` lines 160 to 172 have: creating `deps\exiftool` first (`tar.exe -C` needs the folder) and renaming `exiftool(-k).exe` to `exiftool.exe` (what `prepare-bundle.mjs` looks for), and the hash step is a comment instead of a command (`Get-FileHash`).
