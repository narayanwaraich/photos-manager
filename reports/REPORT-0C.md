### Fix 1: Test the package, not the build folder
The smoke test no longer executes from `src-tauri/target/release/`. Packaging was updated so all runtime dependencies are inside the uploaded bundle artifacts prior to bundling:
- **macOS:** `prepare-bundle.mjs` stages `resources/exiftool` and `resources/fixtures` into `src-tauri/resources/`. `package-bundle.mjs` populates `Contents/Frameworks/` and rewrites all `@rpath` linkages. In CI, `photos-manager.app` is copied to `/tmp/smoke-extracted/photos-manager.app`.
- **Windows:** `tauri.conf.json` maps `"vips_dlls/": ""` and `"resources/": "resources"`. `prepare-bundle.mjs` copies `deps/vips/bin/*.dll` into `src-tauri/vips_dlls/`. The NSIS installer generated by `tauri build` packages all DLLs adjacent to `photos-manager.exe`. In CI, the installer silently installs to `C:\smoke-extracted\` via `photos-manager_0.1.0_x64-setup.exe /S /D=C:\smoke-extracted`.

### Fix 2: macOS Homebrew Fallback Ruled Out
1. **Dynamic Linkage Audit (`otool -L`):**
`package-bundle.mjs` verifies the main binary and all 67 bundled `.dylib`s. Any line containing `/opt/homebrew` or `/usr/local` causes an immediate build failure.
CI output:
```
=== Checking otool -L on main binary for Homebrew / usr/local ===
✓ Main binary clean: no Homebrew or /usr/local references
=== Checking otool -L on all bundled dylibs ===
✓ All bundled dylibs clean: zero Homebrew or /usr/local references
```
2. **Physical Hiding of Homebrew on CI Runner:**
In `.github/workflows/ci.yml`, the runner physically renames `/opt/homebrew` prior to running the smoke test:
```bash
sudo mv /opt/homebrew /opt/homebrew.off
env -i PATH=/usr/bin:/bin:/usr/sbin:/sbin "$EXE_PATH" --smoke-test --out smoke-macos-arm64.json
sudo mv /opt/homebrew.off /opt/homebrew
```
The smoke test executed and passed with exit code 0 while `/opt/homebrew` did not exist on the filesystem.

### Fix 3: Removal of `PHOTOS_DEV_ALLOW_SVGLOAD` Bypass & Untrusted Loader Blocking
1. **Bypass Removed:** The environment variable `PHOTOS_DEV_ALLOW_SVGLOAD` was deleted from codebase and CI scripts.
2. **Startup Blocking Option Used:** Libvips C API blocking combined with environment variable blocking:
   - `std::env::set_var("VIPS_BLOCK_UNTRUSTED", "1");`
   - `libvips::ffi::vips_block_untrusted_set(1);`
   - Explicit operation blocks: `vips_operation_block_set("svgload", 1)` and `vips_operation_block_set("magickload", 1)`.
   - `VipsImageProcessor::query_supported_loaders` tests each candidate loader with `is_loader_supported`, which explicitly rejects `svgload` and `magickload`.
3. **Active Probe:** `scripts/generate-fixtures.py` creates `tests/fixtures/generated/fixture_blocked.svg`. The smoke test attempts to load this SVG; it requires that libvips fails with an untrusted loader error. If loading succeeds, the smoke test halts with code 1.
Smoke verification result:
- macOS: `supported_loaders: ["jpegload", "pngload", "webpload", "tiffload", "gifload"]`
- Windows: `supported_loaders: ["jpegload", "pngload", "webpload", "tiffload", "heifload", "gifload"]`
- Both OSes: `disallowed_loaders_absent: true`, `has_magickload: false`, `has_svgload: false`, `blocked_untrusted_svg_load_verified: true`.

## 7. Real Deviations from Ideal Spec

1. **Untrusted Loader Handling:** A custom compile of libvips without librsvg was not available in Homebrew; instead, untrusted loaders were blocked at startup using C API `vips_block_untrusted_set(1)`, `VIPS_BLOCK_UNTRUSTED=1`, and operation blocks for `svgload` and `magickload`, verified by an active probe loading an SVG fixture.
2. **libvips Windows Binding Fork:** Upstream `libvips 2.3.0` bindings fail to compile on Windows MSVC due to LLP64 integer type mismatches. Photos Manager uses a patched git fork (`kuma-00/libvips-rust-bindings-for-windows`) pinned to commit `80097ad`.
3. **ExifTool Arguments via Stdin:** Passing Unicode and long file paths on Windows via CLI arguments (`lpCommandLine`) results in MSVC CRT ANSI code-page corruption. Photos Manager pipes paths via stdin with `-@ -` and `-charset utf8 -charset filename=utf8`.
4. **Homebrew-Sourced macOS Dynamic Libraries:** macOS dynamic libraries were harvested from `/opt/homebrew` and relocated via `@rpath`. Audit revealed two GPL libraries (`fftw` and `libimagequant`). Production distribution in Phase 7 requires an in-tree minimal Meson build.
5. **macOS ExifTool Relies on System Perl:** On macOS, ExifTool relies on `/usr/bin/perl`. While present on macOS 27 (`v5.34.1`), Apple deprecated scripting runtimes in Catalina; bundling a standalone Perl or pure Rust parser will be required if Apple removes it.

## 8. Items Validated on Only One OS

- **Physical Drive Hot-Unplug & Mount Monitoring:** Validated through unit test logic only; physical USB drive unplug and reconnect is reserved for the owner's Windows PC manual pass (`docs/windows-validation.md`).
- **WebView2 Native Window Rendering:** Tested via headless build in CI; full graphical window rendering and WebView2 interaction are tested manually on the Windows laptop.
- **HEIC Image Decoding:** HEIC decode via `libde265` is currently present only in the Windows minimal build (`heifload`). The macOS Homebrew build omitted `libheif` to avoid GPL `x265`.

## 9. Concepts Used

1. **Dynamic Linking & `@rpath` Relocation (macOS):**
   Unlike static linking, dynamic libraries reference other libraries by install names; `@rpath` allows binaries to look for `.dylib` dependencies relative to their own location (`@executable_path/../Frameworks`) rather than fixed system directories.
   *Example:* [scripts/package-bundle.mjs:141](file:///Users/narayanwaraich/Desktop/Projects/photos-manager/scripts/package-bundle.mjs#L141).

2. **Windows Command-Line Character Encoding & Stdin Argument Files (`-@`):**
   Windows passes arguments as a single UTF-16 string (`lpCommandLine`), but the C runtime of external child processes (most likely inside ExifTool's Perl runtime) converts arguments using the active ANSI code page (e.g. CP1252), corrupting non-ASCII characters. Passing arguments over stdin with `-@ -` bypasses the command line entirely.
   *Example:* [src-tauri/src/metadata/mod.rs:194](file:///Users/narayanwaraich/Desktop/Projects/photos-manager/src-tauri/src/metadata/mod.rs#L194).

3. **Cargo Crates.io Patching (`[patch.crates-io]`):**
   Cargo allows overriding an upstream crate dependency across the entire workspace with a patched git fork without changing the dependency declarations in individual sub-crates.
   *Example:* [Cargo.toml:4](file:///Users/narayanwaraich/Desktop/Projects/photos-manager/Cargo.toml#L4).

4. **Hermetic Packaging Verification (Hiding Developer Paths):**
   To prove an application does not silently rely on developer tools, tests are run with a stripped `PATH` and by physically renaming the developer library directory (`sudo mv /opt/homebrew /opt/homebrew.off`) during execution.
   *Example:* [.github/workflows/ci.yml:178](file:///Users/narayanwaraich/Desktop/Projects/photos-manager/.github/workflows/ci.yml#L178).

5. **Deterministic Toolchain Pinning (`rust-toolchain.toml`):**
   Specifying `channel = "stable"` causes the compiler version to float with upstream releases, whereas pinning `channel = "1.99.1"` guarantees that local machines, CI, and Windows test PCs compile with identical compiler internals, warnings, and code-generation behavior.
   *Example:* [rust-toolchain.toml:2](file:///Users/narayanwaraich/Desktop/Projects/photos-manager/rust-toolchain.toml#L2).
