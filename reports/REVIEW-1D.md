## Findings: code (the fix prompt does these)

**C1 (important): cancelling a scan can hang it forever, and the root can then never be scanned again.** In `scan_root` the writer loop does `if cancel.is_cancelled() { break; }` and keeps `rx` alive until the function ends, then awaits `walk_handle`. The walker (`run_walk`) notices the flag at the top of its next iteration, `break`s, and then runs `if !current_batch.is_empty() { let _ = tx.blocking_send(current_batch); }`. When the writer is slower than the walker (the normal case on a large tree: the channel of capacity 2 is full), that last `blocking_send` waits for a free slot that nobody will ever free, because the writer has left the loop and still holds `rx`. `walk_handle.await` then never returns, `scan_root` never returns, and the `ScanGuard` is never released, so every later scan of that root answers `scan_already_running`. I reproduced the control flow (same capacity, same cancel check, same leftover send, same await) in a 30-line program in my scratch folder: it prints `DEADLOCK: walk thread still blocked after 3s`. **I did not run it against the real code** (the Tauri crate does not build in my session); the existing cancel test passes because its tree has 8 files and the walker finishes before the writer cancels. Fix: after the writer loop and before `walk_handle.await`, `drop(rx)`, so the walker's blocked send fails and the walker returns (the early `return Err` paths drop `rx` already when the function exits). Add the test below.

**C2 (important, found by the real run): the scanner walks into macOS `.photoslibrary` packages.** On the owner's `~/Pictures` the report shows `Photos Library.photoslibrary` and `Photo Booth Library` as `entry_unreadable` (macOS privacy protection). Where access is granted, the scanner would walk into the package and index its `originals/`, `resources/derivatives/` and `thumbnails` as if they were the user's photos. D29(c) already refuses a `*.photoslibrary` as a root because it belongs to another manager. **New decision (m):** a directory whose name ends in `.photoslibrary` (case-insensitive, any OS) is skipped like the always-skipped names (not entered, counted in `skipped_by_rule`). Test: a temp tree with `Some.photoslibrary/originals/a.jpg` and a normal folder; only the normal one is recorded; `skipped_by_rule` counts the package.

**C3 (important): there is no test of the scanner's name rules.** `test_name_rules_and_path_key_collision_carries_existing_id` only inserts two rows by hand with `insert_file` and checks that the repository error carries `existing_id` (the 1A carry-forward: good, keep it). Part C also asked for: a non-Unicode name skipped with `path_not_unicode` (Unix), a name with a backslash or a trailing colon skipped with the 1A code (Unix), and two names that collide by key through a real scan (NFC and NFD forms of one name, or two case variants on a case-insensitive volume): first one wins, the second is reported as `path_key_collision`. None of these runs through `scan_root`. Add them (Unix-only where the filesystem needs it; the NFC/NFD pair only where the filesystem keeps both names, and say which OS ran it).

**C4 (important): the move tests cover one of the four cases the task named, and one design question.** Present: move to another folder with a new name, and a hard-link case (the ambiguous side). Missing: (a) rename inside the same folder, (b) rename a folder (all files inside keep their ids, no `missing` left, no duplicate rows, assets still one per file), (c) a file whose `file_identity` is NULL is never matched (set it to NULL in the catalogue with an `UPDATE`, rename the file, expect new + missing). **New decision (n):** candidates on the stale side exclude rows that were already `missing` before this scan began. Reason: inode numbers are reused after a deletion on common filesystems; a row marked missing months ago must not be revived as another photo's history. A file that was deleted, scanned as missing and restored elsewhere later becomes a new file (costs history, never a wrong merge, the same rule as (h)). Test: delete A, scan (A becomes `missing`), create B, `UPDATE` A's identity to B's, scan: B is new, A stays missing, `moved = 0`. Show this test failing without the filter.

**C5 (important): the interrupted-scan test does not prove its second claim and one scenario is a race.** The gate says: after each interruption, "a later complete scan gives the same database as a scan that was never interrupted". The test ends with `unchanged == 8` and `marked_missing == 0`, which says nothing about equality of rows. Scenario 3 (drop the future) sleeps 5 ms and aborts the task, so it can abort before any batch was committed, or after the scan finished. Fix: (a) a helper that snapshots `folders` and `files` (path_key, status, extension, size, mtime, id excluded or compared as sets, generation excluded) and `assets` counts; assert that the snapshot after the interrupted-then-complete sequence equals the snapshot of a second, never-interrupted database built from the same tree (the first scan of the first test database is not enough, because the interruptions start after a first complete scan; use a tree that changed between the first scan and the interruptions, e.g. delete one file and add two, so the later scan really has work to do); (b) scenario 3 made deterministic: the progress callback sends on a `tokio::sync::oneshot` after batch k, and the test uses `tokio::select!` to drop the scan future when it arrives; (c) a new scenario 5 for C1 below. Keep the existing "no row is missing that exists on disk" assertions.

**C1 test:** `#[tokio::test(flavor = "multi_thread")]`, a tree of at least 300 files, `batch_size: 1`, the progress callback sleeps 20 ms (`std::thread::sleep`) and cancels after the first batch; the whole `scan_root` call runs inside `tokio::time::timeout(Duration::from_secs(10), ...)`; assert it returns `Cancelled`, then that a second `scan_root` for the same root starts (the guard was released). **Show this test failing (timing out) with the `drop(rx)` removed**, then passing.

**C6 (important): two tests are not testing the scanner on Windows.** `test_warnings_capped_at_100` has a `#[cfg(not(unix))]` branch that builds its own `Vec` and counts to 120 without calling the scanner: it passes on Windows whatever the scanner does. `test_unreadable_directory...` is `#[cfg(unix)]` only, so on Windows nothing tests the carry-over (the task said: test the logic through an injected hook). Fix: move the body of the writer loop's per-batch work into a function `apply_batch(tx, items, state, ...)` (private to `scanner/`), so a test can feed it synthetic `WalkItem`s: (a) 120 `WalkItem::Warning`s give `warning_count = 120` and 100 stored; (b) a `WalkItem::InaccessibleDir` for a folder that has rows below it marks the subtree `inaccessible` and the final marking does not make any of it `missing`. Those run on both OSes; keep the Unix `chmod` tests as they are.

**C7 (blocking until explained): CI run `45106237159` is red.** The Mac `pnpm verify` is green (133 passed, 2 ignored), so the failure is on Windows or in `cargo deny`. I do not know which. The owner supplies the tail of the failed log (NEXT_STEPS step 1); the agent fixes the cause and the report shows the log tail. Candidates, not checked: an unused import or function on Windows under `clippy -D warnings` (`tests.rs` has `#[cfg(unix)]` tests and top-level imports such as `Ordering`, `Arc`, `Instant`, `FolderStatus` that may be used only there, the same kind of `dead_code` finding as 0F); a Windows-only failure in a test that writes files and renames them; a hung or slow Windows test. Do not guess: read the log.

**C8 (small): the `Err` branch of the walk misclassifies a failed stat.** In `run_walk`, `let is_dir = path.is_dir() || err.depth() > 0;` is true for every error below the root, so `InaccessibleFile` is dead code for walkdir errors and a file that cannot be stat-ed is never marked `inaccessible`. Use `path.is_dir()` alone and add a small test through `apply_batch` (C6) for `InaccessibleFile`.

**Nits (note in the report, fix if cheap):** the parent lookup is written twice in `scan_root` and falls back to `FolderId::from(String::new())` (an empty id that would fail the foreign key; return an error instead); the 5,000-file test asserts counts only (the bound is the channel capacity, which the report explains; acceptable); `ScanOptions` carries test hooks in the production struct (the task asked for it).
